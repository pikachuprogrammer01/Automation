# 自动化管理器 PRD

版本：v1.0.0 对应 · 最后更新 2026-10-02
状态：本文描述**已实现的行为**。未实现的东西不出现在正文，只在「非目标」里明确排除。

## 一句话

一个跑在 macOS 本机的定时网页任务管理器：把浏览器操作录成 Playwright 脚本，交给系统 launchd 每天准点执行，并在网页界面上看清每一次到底成了没成、没成是为什么。

不是云服务，不是机器人平台，不是 LLM 代理。它解决的是"我有三五个网页每天要点一下，不想为这事开一台机器"。

## 目标用户

| 用户 | 他要做的事 | 现在能不能做 |
| --- | --- | --- |
| 会写一点代码、不想搭 Selenium 框架的个人 | 录制 → 改脚本 → 定时 → 看结果 | 能，全流程界面化 |
| 完全不会写代码的个人 | 录制 → 定时 → 看结果 | 能，第 ③ 步"打开代码"是可选的 |
| 需要凭据管理的用户 | 口令进 macOS Keychain，脚本里不出现明文 | 能（专属 Profile 登录态或 Keychain 两种） |
| 要跑在服务器上/多机同步的团队 | — | **不能，非目标** |

## 问题陈述

"每天打开某个网页点一个按钮"这件事，现有做法各有过不去的坎：

- **crontab + 手写脚本**：凭据要么写在脚本里要么写在 env 里；失败只有一行 exit code；页面改版后你不知道，直到某天发现连续 30 天没签到。
- **浏览器插件定时**：机器不能锁屏，锁了就停。
- **RPA / LLM 自动化平台**：为一天一次点击引入常驻服务、向量库、模型调用，成本和不确定性都远超问题本身。

本产品的取舍是：**执行层就是 Playwright 脚本 + launchd，没有中间层**；产品价值集中在"录制门槛"和"结果可解释"这两点上。

## 产品原则

这五条是从代码里读出来的，不是愿望。

1. **无事可做不等于失败。** 这是产品鼓励并示范的约定：脚本遇到"今天没有可领的东西"应当成功退出并写明原因，而不是报警。管理器如实呈现退出码，`/demo/` 的文案与示例判定标记刻意保持一致，就是为了把这条约定演示清楚。**反向同样成立：没跑不成"无事可做"。** 并发锁里记持有者 pid；上一轮被强杀留下的锁会被接管，运行记录带上 `lockStale: true`，而不是每天报一个 `skipped` 加退出码 0 —— 那会把永久停跑伪装成无事可做。
2. **失败必须能自己看懂。** 每个错误带 `code` + 人话 `error` + `hint`；服务端异常指向具体日志文件。
3. **凭据不出机器。** 口令只进 macOS Keychain；登录态存在任务自己的 `auth.json`（0600）；界面和接口不回显口令。
4. **不提供任意命令执行。** 接口只能操作登记表里已有的任务，没有 shell 入口。
5. **默认值要能直接活。** 零 npm 依赖起服务；构建产物入库；一个 `cp` + 一条 `npm start` 就能看到界面。

## 功能范围

### 任务生命周期

| 能力 | 行为 | 实现位置 |
| --- | --- | --- |
| 新建 | 录制操作 / 新建空白脚本两种方式，生成 `var/tasks/<id>/` 脚手架 | `POST /api/recordings/create` |
| 定时 | 写任务自己的 LaunchAgent plist，`Hour`/`Minute` 精确到分钟 | `installTask` |
| 启用 / 暂停 | 加载或 bootout + `launchctl disable` | `enableTask` / `disableTask` |
| 修改时间 | 重写 plist 并重新 bootstrap | `POST /api/tasks/:id/schedule` |
| 移除定时 | 只删 plist，保留脚本、登录态、Profile、日志 | `removeSchedule` |
| 彻底删除 | 逐项勾选是否连凭据/Profile/日志一起删，且必须原样输入任务 ID 确认 | `purgeTask` |
| 立即运行 | 手动触发一次，与定时互不干扰 | `runTask` |

### 录制与调试

`① 准备登录`（独立 Chrome Profile，关窗自动导出 `auth.json`）→ `② 开始录制`（`playwright codegen --channel=chrome`）→ `③ 打开代码`（VS Code，退化为文件管理器定位）→ `④ 可视化测试`（带界面跑一次）。

### 结果可解释

- **运行输出面板**：每 1.5 秒按字节偏移拉增量日志，所以两个账号共用一个日志文件也不会串台；结束时把状态翻成「成功 · 用时」或「失败 · 退出码 · 用时」，只提示一次；关掉后卡片上仍保留上次运行摘要和「看输出」，随时回看同一次输出。
- **任务状态四态**：`运行中`（含具体是运行/录制/登录/测试）· `已启用` · `已暂停`（plist 在但没加载）· `未启用`。
- **连接状态四态**：`管理器运行中` · `管理器已关闭`（你主动关的，重开 App 即恢复）· `连接中断`（进程没了）· `后端异常`（进程在但接口不对，含"这个端口上应答的不是自动化管理器"）。页面切到后台停止轮询，回前台立即刷新一次。
- **并发保护**：同一任务在跑时，四个触发按钮按住（后端 `task_busy` → 409），不会出现连点多次却不知道在跑什么。

### 内置演示站点

`/demo/` 是随构建产物入库的纯本地假站点：不联网、状态存 localStorage、有重置按钮。它的按钮文案与"已领取不该算失败"这类判定示例严格对应，页面自带重置入口，所以可以反复录、反复测，练手成本为零。想试录制流程又不想拿真实站点练手的，用它。

### 配置与隔离

端口、数据根目录、登记表路径、launchd 标签前缀全部可用环境变量覆盖；`manager/install-launchagent` 负责生成后台服务。数据根与登记表同源，所以 `AUTOMATION_HOME` 一个变量就能把两者一起搬进沙箱。详见 `../README.md` 的环境变量一览。

## 非目标

以下每一条都是**故意不做**，不是没做。提这些方向的 issue 大概率会被关。

| 非目标 | 为什么 |
| --- | --- |
| Linux / Windows | 调度、凭据、进程托管全建立在 launchd + macOS Keychain + `security` 上。换平台等于换实现。 |
| 云端、多设备同步、账号体系 | 它是个本机工具。加登录就变成服务，需要运维的就不再是个人项目。 |
| 对外网开放 / 部署成网站 | 只绑 `127.0.0.1`。这不是安全加固，是产品边界。 |
| 站点脚本市场 / 现成站点适配 | 发布版只带本地演示站点。真实站点的 runner 是使用者自己的东西。 |
| 反爬、代理池、验证码与 MFA 绕过 | 管理器本身不提供任何绕过能力，也不内置这类逻辑 —— 它执行的就是你自己那段 Playwright 代码。作者自己的 runner 遇到条款弹窗或安全校验一律失败退出并留证据，但那份 runner 不随发布版分发。 |
| LLM 决策 / 自然语言驱动 | 脚本是确定性的 Playwright 代码，可 diff、可 review、可自己改。 |
| 任意 shell / 自定义命令执行 | 接口只能操作登记过的任务。开了这个口子，本机权限就没了边界。 |
| 并行调度、任务依赖编排 | 一天几个任务的量级不需要 DAG。 |
| 移动端界面 | 响应式不是目标，这是坐在电脑前用的东西。 |

## 约束与假设

- 单用户、单机、本机使用。没有并发多管理员的场景。
- 依赖系统 Chrome（路径写死在 `manager/server.mjs`），不下载 Playwright 自带浏览器。
- 定时精度受 launchd `StartCalendarInterval` 限制，只到分钟。**机器睡眠期间错过的触发会在唤醒后补跑一次**（与 cron 不同；睡眠期间跨过的多个时间点会合并成一次），所以合盖过夜、第二天开盖会看到一次迟到的运行。关机期间错过的不补。
- 录制脚本随目标站点改版而失效，这是使用成本，不是产品缺陷。
- 端口默认 4765，只绑回环。

以 2026-10-02 的一次 `/devex-review` 实跑为基线。下表每一条都可以通过照 `README.md` 走一遍复现，不依赖任何未发布的内部数据。

| 指标 | 基线 | 判定 |
| --- | --- | --- |
| 从零到看到界面 | 拿到文件 → `cp` 种子登记表 → `npm start` → 首个 200，0.1 秒 | 达标：零 npm 依赖、无需构建 |
| 首次录制练习 | `/demo/` 可直接录，不联网、不碰任何真实站点 | 达标 |
| 错误可诊断性 | 17 项入参/状态探测全部返回语义状态码 + 人话 + `hint` | 达标 |
| 凭据处理 | 口令只进 Keychain；`auth.json`（运行期生成）与私有数据文件一律 0600 且在 `.gitignore` 内 | 达标 |

| 发布物洁净度 | 私有层与运行数据分别落在 `private/` 与 `var/`，由**入库的** `.gitignore` 两行规则排除 | 达标（边界随仓库走，不再依赖建仓时的人工剔除，也不再依赖 `git add -A` 之前记得补本地 exclude） |

## 验收标准

改动命中下列任一条路径时，必须逐条验过再合：

1. **任务全生命周期**：建 → 定时 → 启用 → 立即运行 → 暂停 → 移除定时 → 彻底删除（confirm 不匹配必须被拒）。
2. **录制链路**：`① 准备登录` 关窗后 `auth.json` 生成且权限 0600；`② 开始录制` 产出 `recorded.spec.js`；`④ 可视化测试` 在无头/有头两种模式下都能拿到退出码。
3. **并发**：同一任务运行中重复触发返回 409，界面按钮按住。
4. **共享日志**：两个任务指向同一日志文件时，各自面板只看到自己那段。
5. **示例与文档一致**：`/demo/` 的按钮文案与 README/本文里引用的判定示例必须同步改。演示站点的价值就在于"文案与判定标记一致"，不同步即失效。
6. **状态语义约定（作者私有层）**：站点 runner 遇到"今天无可领"判 `completed`，真失败留 `note` 与证据路径。这条不在发布仓内，但改示例时必须保持同一套语义，否则文档与代码会分叉。
7. **回归隔离**：任何写操作的测试必须打在隔离实例上（`AUTOMATION_HOME` 指向沙箱 + 假 `HOME`），并在结束时断言生产 `var/registry.json` 与生产任务未被触碰。
8. **不启动生产**：验证 `open-manager` / `install-launchagent` 的失败分支时，不得对真实 launchd 域执行 `kickstart` 或 `bootstrap`。

## 度量与反馈

- 无遥测、无埋点。本机工具不往外发任何东西，这条不会因为"想知道大家怎么用"而改变。
- 唯一的反馈通道是 issue。测试与 CI 的覆盖范围见 `../README.md`「测试」一节；issue 里请附 `automation-log --run <runId>` 的输出与 `var/logs/` 片段。
- 欢迎的 issue：可复现的 bug、文档错误、对「非目标」边界的质疑（带理由的那种）。
- 不太欢迎的 issue：直接要求实现「非目标」表里的东西、跨平台移植、"能不能接 GPT 自动写脚本"。

## 版本与变更纪律

- 当前 `1.0.0`，没有 CHANGELOG，没有迁移脚本。历史上破坏性变更（例如端口 8765 → 4765）目前只在维护者交接文档里留档，发布版没有对等的记录 —— 这是缺口，不是设计。
- 登记表有 `version` 字段但**没有读取和迁移逻辑**。任何破坏 `registry.json` 结构的改动，在补上迁移代码之前都不该发。
- 建议口径：只在有对外可用变化时升版本，且先补 CHANGELOG 再发。

## 风险与开放问题

1. **目标站点的服务条款是否允许脚本化访问，未做评估。** 这是使用者自己的判断，作者不做背书 —— 也是发布版不带站点专用 runner 的原因。
2. **`manager/server.mjs` 的纯函数尚未与副作用分离**（`fromPortable`/`plistText`/入参校验），所以它本身拿不到单元覆盖；目前靠 API 契约层与生命周期层从外部压住行为。
3. **`open-manager` 的两条失败分支未做运行时验证**（会重启生产服务或注册真实 launchd 任务），只有静态保证。
4. **录制脚本的可维护性归使用者。** 站点改版导致失效，产品不提供任何自愈能力。
